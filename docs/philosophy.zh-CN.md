# AutoBoard：理念与使用最佳实践

英文版：[philosophy.md](./philosophy.md)

## 它解决什么问题

AI Agent 已经能跨仓库、跨会话做实质工作，但团队协作里最常缺的一层信息是：

> 现在各项目里，谁在查什么线上问题、在改哪个 bug、在推哪条需求，状态如何，上一轮做到哪了。

传统看板依赖人手工拖卡片；Agent 时代更常见的是「对话里做完了，看板上一片空白」。AutoBoard 的定位很窄、也很硬：让 **Agent 自己把进展写到一页看板上**，让人不用追问就能看见。

它不是项目管理系统，不是工单中心，也不是聊天记录归档。它只回答一件事：**各项目当前在飞什么，以及最近一次真实进展是什么。**

---

## 核心理念

### 1. 上报必须极轻，绝不能挡工作

上报方式就是一次 HTTP POST。不依赖本机脚本路径、不绑定某台机器、不要求先 clone 看板仓库。连不上板就跳过，继续做事。

上报脚本的硬约束是：`exit 0`、不抛未捕获异常、不长时间阻塞。理念很清楚——**看板是旁路观察，不是主流程门禁。**

### 2. 提出 ≠ 要做

很多系统把「登记」和「开工」混成一步，看板立刻变成「全员 `in_progress`」。AutoBoard 把确认拆成独立阶段：

- `pending`：刚提出，还没定是不是真问题、要不要做
- `confirmed`：拍板要做，但还没动手
- `in_progress`：真的在写代码或改配置
- `rejected`：误报、重复、被砍——和 `done` 严格区分

一登记就写 `in_progress`，会让别人误以为已经有人在干。

### 3. 状态枚举要死，细节写进 progress

状态只允许固定集合，禁止自由文本状态列（例如 `MERGED_TEST04_E2E`）。合到哪个环境、哪个 commit、为什么否决——全部写进 `progress`。

项目存在的一个理由，就是 **用有限状态 + 可读进展，取代无限膨胀的状态字段。**

### 4. 线上排查与 bug/需求平级

`incident` 不是附属标签。很多时候还没定性成缺陷，但「谁正在查什么线上问题、已经查了多久」本身就是看板最该暴露的信息。

排查用 `event: start/end` 记区间，和 `status` 正交：可以一边 `in_progress` 一边「排查中」，也可以排查结束仍留在 `in_progress`。

### 5. 幂等 upsert，标题即身份

同一件事靠 `项目 + id` 或 `项目 + 归一化标题` 命中同一行。后续上报必须 **标题一字不变**，或带上首次返回的 `id`。改标题重试，只会制造重复条目，并让 `end` 算不出耗时。

### 6. 事件只追加，不改写历史

底层是 append-only 的 `events.jsonl`，坏行跳过也不妨碍启动。看板展示的是投影，真相是事件流——适合 Agent 高频、偶发脏数据的上报场景。

### 7. 零依赖、自托管、协议三点同步

运行时零 npm 依赖，单文件 UI，Docker 单副本。协议变更必须同时改 schema、Skill 模板、安装进仓库的 AGENTS 段落，否则各仓库会漂移。

公开演示站只用于预览；**团队应部署自己的实例，上报指向自己的 URL。**

## 使用最佳实践

### 部署

1. 用 Docker 起自己的实例，数据落在宿主机 `./data`，只跑一个副本。
2. 需要公网时前面加反向代理；设置 `BOARD_PUBLIC_URL`，保证 `/install.mjs` 内嵌的是对外地址。
3. 写接口建议设 `BOARD_TOKEN`；Agent 上报带 `Authorization: Bearer …`。
4. 不要把生产上报打到公开演示站。

### 装进业务仓库

在业务仓库根目录执行安装脚本（不必克隆看板仓库），把 Skill 与 `AGENTS.md` 段落 **提交进 git**，让所有人和所有 Agent 共用同一看板 URL。

协议升级后，对业务仓重新跑一次安装，避免 Skill 与服务端枚举不一致。

### 什么时候该报 / 不该报

**要报：** 开始或结束线上排查；新登记 bug/需求；确认做或不做；定位根因；推进或完成；提交评审；被阻塞；状态变化；本轮有实质产出。

**不要报：** 纯问答、只读浏览、本轮没有任何进展变化。一轮对话同一条目只报一次，避免刷屏。

### 怎么写字段

| 字段 | 实践 |
|---|---|
| `title` | 一句话说清是什么；同一件事永远复用同一标题 |
| `progress` | 写「做了什么 / 卡在哪」，不要写「我在处理这个问题」 |
| `status` | 新建默认 `pending`；只追加进展时省略 `status`，避免误改状态 |
| `event` | 仅排查用 `start`/`end`；普通进展不要带 |
| `id` | 首次返回后记住，后续优先带 `id` |
| `actor` | 用 `git config user.name`，不要长期落成 `unknown` |

主干路径：`pending → confirmed → in_progress → review → done`。`rejected` 可从任意阶段进入。只有「自己发现、当场就修」才适合从 `pending` 直接跳到 `in_progress`。

### 排查计时

接到线上反馈立刻 `start`，不要等查清再报。结束时 `title` 必须与开始一致；结论写进 `progress`，并落到正确状态（修好 / 转 bug / 误报 / 阻塞等）。中途有线索用普通进展，不要重复 `start`。

### Agent 协作习惯

1. 实质性工作结束前报一次，而不是每改一个文件报一次。
2. 上报失败不重试打断主任务。
3. 看板可读性优先：团队若跨语言，`title`/`progress` 约定统一语言。
4. CLI 只是 curl 的便利封装；没有本地仓库就用 curl，两者等价。

## 常见反模式

1. **一登记就 `in_progress`** — 看板失去「待确认 / 待开工」信息。
2. **每次更新改标题** — 产生重复行，排查耗时断裂。
3. **用 status 塞交付细节** — 枚举膨胀，过滤与协作失效。
4. **把 `rejected` 写成 `done`** — 「不做」和「做完」语义被抹平。
5. **为上报阻塞对话** — 违背旁路原则。
6. **只装 Skill 不提交** — 队友 Agent 仍指向错误或空板。
7. **多副本写同一数据目录** — 与单副本 append-only 设计冲突。

## 一句话收束

AutoBoard 相信：在 Agent 成为主要执行者之后，协作瓶颈不再是「会不会写代码」，而是「别人能不能不用问就知道你在干什么」。

它用极轻的上报协议、严格的状态纪律、以及「提出与开工分离」的流程，把分散在各对话里的实质进展，收敛成一页可信的实时投影——**让 Agent 自动记账，让人只负责决策与同步。**
